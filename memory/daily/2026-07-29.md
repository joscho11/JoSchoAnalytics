## Streamlit throttle — third pass

Throttling recurred after `74d1ad7` (2026-07-24) and `c5a10ec` (2026-07-28), both of which
cut real cost, so this pass measured instead of reasoning. Two harnesses now live in
`scripts/`: `bench_pages.py` (fresh interpreter per page — CPU, wall, peak RSS, module and
heavy-package set, Streamlit cache cardinality and retained bytes, every outbound TCP
connect; cold and warm; `--walk` runs all nine pages in ONE process; `--online` counts real
egress) and `bench_server.py` (the real `streamlit run` process — boot-to-HTTP-200, two idle
windows, a static GET, and the watched-source-file count).

**Environment parity changed the numbers, so it is the first thing to get right.**
`.venv-test` pulls `matplotlib` transitively through `catboost`, and
`pandas.io.formats.style` imports matplotlib when it is present (guarded with
`try/except` → `has_mpl = False`, so production is fine without it). Any such environment
**overstates** the Draft Board and Weekly Fantasy cold cost by ~0.27 CPU-s and ~25 MB. All
headline numbers come from a throwaway venv holding exactly `requirements.txt` + pytest +
psutil, matplotlib confirmed absent.

Headline measurements: a complete production visit to all nine pages in one process costs
**2.53 CPU-s** and peaks at **218.4 MB RSS** (offline: 1.95 CPU-s / 157.5 MB). Real server
boot 1.56 s wall / **0.63 CPU-s** / 80.9 MB. Idle server **8.75 and 10.94 CPU-s per hour**
across two 180-second windows — about 0.3% of one core — and materially unchanged with
`server.fileWatcherType` set to `none`, `poll` or `watchdog`, so the file watcher is not a
factor (`watchdog` is a hard Streamlit dependency off macOS, so Cloud gets the event-based
watcher anyway). Warm reruns are 0.05–0.14 s wall. Worst cold page is the Draft Board at
0.77 CPU-s / 145.7 MB.

Streamlit documents approximate limits of **0.078–2 cores** and **690 MB–2.7 GB** (storage
≤ 50 GB), and says an app at or over its limits may be throttled. It documents **no throttle
accounting window** — no averaging period, no quota, no per-app usage history — so there is
no honest way to express the app's draw as a percentage of a budget, and the report no
longer tries. What can be said is a scale comparison: idle draw ~0.3% of a core, peak RSS
~32% of the documented 690 MB minimum.

Audits all came back negative. **Caches:** 16–17 entries totalling 2.21 MB after touching
every page; every key is a file fingerprint, a season or a draft class (finite domains); no
session scoping; `cache_resource` unused; the one large production object (the nflverse
season pull) is trimmed to 14 of 145 columns before caching. TTL-driven recomputation was
measured rather than assumed — `load_tracker` 0.78 ms, `load_totals_tracker` 0.78 ms,
`_compute_hc_stats` ~0 ms (there is exactly one 12 KB `agent_analysis_*.json`),
`_load_board_2026_cached` 43.75 ms, `_load_college_wr` 6.25 ms, `_board_source_fingerprint`
0.94 ms for its 32 `stat()` calls: **~55 ms if every TTL expired at once.** That does not
justify editing working cache code, so none was edited. **Reruns:** zero occurrences of
`st.rerun`, `experimental_rerun`, `st_autorefresh`, `run_every`, `st.fragment`, `while True`
or a query-param write anywhere in the runtime surface; the only concurrency is League
History's 6-worker matchup pool behind an explicit Load submission.

**Deployment churn was measured and cleared as a CPU driver.** The heaviest push in the
window (`787486c`, "experimenting with hc/oc features") carried 41.75 MB of new blobs — it
is `fantasy/projections/coaching/data/wikipedia_team_season_cache.json`, which the live app
never opens — but packs to only **9.85 MB / 0.9 s**; six of the eight pushes are under 1 MB
packed, and the bot's daily board refresh is the smallest of all (0.01 MB, 5 objects,
0.03 s). Charging every restart a full boot plus a complete cache re-warm gives ~21 CPU-s
per day against 86,400 seconds of wall clock. Separately, the container carries a
**266–293 MB** checkout (full clone 19.1 s, shallow 10.4 s) to serve the **4.54 MB across 32
files** the app actually opens, plus 160 KB of repo `.py`; dependency install is 48.6 s and
600 MB of site-packages but only reruns when `requirements.txt` changes.

The push↔throttle correlation **cannot be computed**: no artifact records a throttle window,
Community Cloud exposes no per-app resource history, and the app logs are only visible live.
A direct probe found the app healthy — HTTP 200 in 1.39 s after three redirects through
`share.streamlit.io/-/auth/app`, the normal 5,843-byte shell, no hibernation or
resource-limit page.

### Changes

`runtime_telemetry.py` (new) plus two lines in `app.py` records process start, per-process
script-run count, a per-process session ordinal, selected page title, CPU delta, wall time,
RSS and peak RSS as one `JSA_TELEMETRY` JSON line per run on stderr — the app log being the
only durable sink on an ephemeral container. **Off unless `APP_TELEMETRY=1`** (env var or
Cloud Secret), **zero new dependencies** (`resource` / `os.times` / `/proc/self/statm`, so
`requirements.txt` stays at eight packages), **no personal data** (no IP, user agent,
referrer, query string, cookie or stable identifier; a test asserts the forbidden field
names never appear), **6.7 µs per run enabled / 0.9 µs disabled** — down from 922 µs after
resolving platform capability once at import instead of swallowing an exception per metric
read on non-Linux.

The GA pageview beacon left the first-render critical path. It was a synchronous
`requests.post` with `timeout=3` inside `site_pageview_once()`, which runs *before*
`st.navigation`, so every session's first render waited on it; measured round trip to
`google-analytics.com/mp/collect` is **223.6 ms mean / 234.6 ms max** over five attempts.
It now goes on a one-shot daemon thread with endpoint, params, payload and timeout
byte-identical, every `session_state` read still on the script thread, and a fallback to the
old inline call if thread creation is refused.

Recommended isolation is a **`streamlit-prod` branch** (local pointer created; pushing it and
repointing the Cloud app are Joseph's), justified on availability — a visitor landing on a
cold process pays 1.03–1.36 s versus 0.06–0.14 s warm, and six of eight pushes touch only
research paths — and blast radius, explicitly **not** on CPU. A separate lightweight repo was
rejected (288 MB saved against a 50 GB allowance, at the cost of a sync job, duplicated
shipped artifacts and the footer's public-repo promise) and so was externally fetching the
ADP overlay (it targets the smallest of the eight pushes and puts a network dependency on the
board's critical path). **Trap if the branch is adopted:** `board_refresh.yml` checks out and
pushes to `main`, so the live board would silently stop refreshing; the workflow was left
unedited because the branch is not yet in use.

## Correction pass (2026-07-30)

**Telemetry concurrency defect, found and fixed.** The first version held each run's start
time, CPU baseline and sequence number in module globals. Streamlit runs every session's
script on its own ScriptRunner thread, so overlapping sessions shared that state: a second
session's `begin()` overwrote the first's baselines, and the first session's `end()` then
emitted the *other* run's elapsed time under the *other* run's `run_seq` — a duplicated
sequence number on a misattributed measurement, in the one instrument whose whole purpose is
counting runs correctly. Per-run state now lives in `threading.local()`; the process-wide run
counter, session ordinal and once-only boot flag are mutated only under a lock; `end()`
clears its thread-local baseline so a stray second `end()` cannot re-emit.

Four deterministic tests were added: an Event-choreographed pair of overlapping runs (a long
run whose window strictly contains a short one), N threads held inside `begin()` by a
barrier, a boot-emitted-once check, and an `end()`-without-`begin()` guard. **Both
concurrency tests were re-run against a shim that re-attaches the pre-fix module-global
`begin`/`end` to the live module and confirmed to fail there** — `duplicate run_seq 2` and
`duplicate run_seq values: [10, 10, 10, 10, 10, 10, 10, 10]` — so they are a real guard
rather than a tautology. `tests/test_runtime_telemetry.py` is now in **both** explicit lists
in `.github/workflows/test.yml`: the `pytests` job (14 files) and `deploy-parity` (9 files).

**Two overclaims withdrawn from `memory/streamlit-throttle.md`.** The verdict "the deployed
application's CPU cannot cause this" overstated what was measured and is now "no measured
sustained application-side resource problem was found" — absence of a measured problem is
not proof of absence, and a burst, a pathology under real concurrent sessions, or an
accounting rule I cannot see would all look identical to these numbers. And the 0.078-core
documented minimum had been multiplied into a "281 CPU-s/hour guaranteed budget" with
percentages derived from it; Streamlit documents approximate min/max allocations and **no
accounting window**, so that arithmetic was mine, not theirs, and every derived percentage is
withdrawn. Benchmark numbers are unchanged throughout, and the report now marks the
measurement/inference boundary explicitly.

**Validation:** telemetry suite 11 passed; the exact minimal-runtime dashboard suite
(deploy-parity list, now including telemetry) 70 passed; all-page AppTest passed;
`test_app_talent_columns.py` + `test_page_rookie_board.py` 8 passed — all under the
requirements.txt-only venv. Benchmarks were not re-run (the telemetry change is inert when
disabled); an entrypoint regression check moved cold CPU 0.547 → 0.625 s and warm 0.042 →
0.042 s, inside the spread already seen between before/after pairs on this box.
